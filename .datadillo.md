# Datadillo review guidance — skaledata/deploy-action

A GitHub Action published for customers to invoke SkaleData deploys from
their own workflows (typically `on: push` to deploy Airflow DAGs / images
to their SkaleData cluster). Consumers pin us via
`skaledata/deploy-action@v1` (or a specific SHA), so the `action.yml`
contract IS the API.

## Highest-signal review dimensions (in order)

1. **Backward compatibility of `action.yml`.** Inputs, outputs, and their
   default values are the public contract. Renaming an input, removing
   one, or changing a default is a breaking change — flag hard, and
   require a major-version tag (`@v2`) rather than shipping under `@v1`.
2. **Shell injection safety.** If this is a composite action that
   interpolates inputs into shell commands, every `${{ inputs.foo }}` in
   a `run:` block is a potential injection vector. Wrap inputs in env
   vars first, then reference them as `"$FOO"` in shell — never inline
   the expression into the command line.
3. **Secret handling.** Inputs that carry secrets (`api-key`, `token`)
   must be documented as such, and MUST NOT be echoed. Watch for
   `set -x`, `echo "$INPUT"`, or `run:` blocks that print env before
   the sensitive step.
4. **Pinned dependencies.** If the action shells out to `skale` (the
   CLI) or curls a release URL, pin the version. Never pull from a
   moving tag like `latest` — a compromised or accidentally-broken CLI
   release would silently break every downstream customer workflow.

## Repo-specific gotchas (flag these hard)

- **`branding.icon` / `branding.color` in `action.yml`** — cosmetic but
  can regress the marketplace listing if removed. Flag if a diff drops
  either.
- **Node action vs. composite action drift.** If this is a Node action
  (`runs.using: node20`), the `dist/` folder must be regenerated and
  committed after any `src/` change. A stale `dist/` silently ships the
  old code — flag when `src/` changed but `dist/` did not.
- **Cross-platform runners.** GitHub Actions supports `ubuntu-*`,
  `macos-*`, and `windows-*` runners. If the action assumes bash /
  `/tmp` / etc., document the supported runners in the README.
- **Semver tag hygiene.** Consumers pinning `@v1` expect us to move the
  `v1` tag forward on non-breaking changes. Flag any release notes that
  imply breaking changes will be shipped under an existing major tag.

## What to skip

- README wording tweaks with no code impact.
- LICENSE / `.gitignore` chores.

## Tone

Terse. Any change to `action.yml` is potentially breaking — call the
compat class (patch / minor / major) explicitly.
